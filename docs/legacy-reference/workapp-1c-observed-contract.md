# WORKAPP / 1С — наблюдаемый контракт Legacy

Статус: черновик по коду Legacy, не официальный контракт 1С.

Этот документ фиксирует только то, что реально видно в репозитории. Значения авторизации, телефоны, персональные данные и другие секреты намеренно не включены. Поля, форматы ошибок, правила повторов и бизнес-семантику должен подтвердить владелец WORKAPP/1С.

## 1. Клиент и бонусы: WORKAPP

Базовый адрес в Legacy зашит как HTTP endpoint WORKAPP. В production необходимо подтвердить актуальный HTTPS-адрес, TLS, авторизацию и сетевые ограничения.

### Получение клиента

`GET /Vizaje-Nica/hs/WORKAPP/GetCustomerByPhone/{phone}`

Наблюдаемая логика:

- перед запросом из телефона удаляются `+`, `(` и `)`;
- сначала отправляется номер в международном формате;
- если в ответе нет `Discount`, выполняется повторный запрос с заменой префикса `373` на `0`;
- из ответа используются поля `Discount`, `Code` и `Name`;
- `Code` используется как идентификатор для запроса бонусного остатка;
- `Name` разбирается на имя и фамилию по пробелу.

Ожидаемый минимальный shape ответа по коду:

```json
{
  "Code": "<customer-code>",
  "Name": "<customer-name>",
  "Discount": 0
}
```

### Получение бонусного остатка

`GET /Vizaje-Nica/hs/WORKAPP/GetBonusAccum/{Code}`

Ожидаемый минимальный shape ответа:

```json
{
  "Bonus": 0
}
```

Legacy записывает полученные `Discount` и `Bonus` в локальную таблицу `clients`. Это выглядит как локальный snapshot, а не как источник истории операций.

### Передача данных клиента

`POST /Vizaje-Nica/hs/WORKAPP/PostCustomerInfoByPhone`

Наблюдаемый JSON-запрос:

```json
{
  "Phone": "<normalized-phone>",
  "Name": "<name>",
  "Surname": "<surname>",
  "BirthDate": "YYYYMMDD"
}
```

Если имя, фамилия или дата рождения отсутствуют, Legacy подставляет значения по умолчанию. Нужно подтвердить, допустимо ли это в новой системе и какие поля обязательны для 1С.

## 2. Заказы: Legacy → 1С

### Получение новых заказов

Маршрут сайта: `api/order_json`, контроллер `application/controllers/Api.php::order_json()`.

Наблюдаемая модель:

- выбираются строки `orders`, где `1c = 0`;
- заказ идентифицируется внешним `order_id`, возвращаемым как `id`;
- передаются `status`, `total`, `delivery_price`, имя, фамилия, email, телефон, адрес, дата создания;
- `payment` дополнительно передаётся как числовой код и человекочитаемый `payment_name`;
- позиции передаются как `id`, `quantity`, `price`, `options`, `SKU`, `variable`;
- `variable` — SKU варианта из `products_variable`, если вариант выбран;
- ответ — JSON-массив заказов.

Пример shape без реальных данных:

```json
[
  {
    "id": "<order-id>",
    "status": "<status>",
    "total": 0,
    "delivery_price": 0,
    "name": "<name>",
    "surname": "<surname>",
    "email": "<email>",
    "phone": "<phone>",
    "address": "<address>",
    "added": "<datetime>",
    "payment_name": "Cash|Card|Online",
    "payment": 1,
    "products": [
      {
        "id": 0,
        "quantity": 1,
        "price": 0,
        "options": 0,
        "SKU": "<product-sku>",
        "variable": "<variant-sku-or-empty>"
      }
    ]
  }
]
```

### Подтверждение заказа

Маршрут: `api/order_check`, контроллер `application/controllers/Api.php::order_check()`.

Наблюдаемая модель:

- принимает внешний `id` заказа;
- ищет `orders.order_id`;
- при найденном заказе устанавливает `orders.1c = 1`;
- возвращает тот же shape заказа;
- если заказ не найден, возвращает текстовую ошибку;
- если `id` не передан, возвращает текстовую ошибку.

### Что обязательно подтвердить у 1С

- является ли `1c` только флагом доставки или существует отдельный статусный обмен;
- может ли 1С запросить один и тот же заказ повторно;
- что происходит при таймауте после получения, но до подтверждения;
- должен ли `order_check` быть идемпотентным;
- какие статусы заказа считаются принятыми, собранными, отгруженными, отменёнными и возвращёнными;
- каким идентификатором заказ живёт в 1С;
- как передаются промокоды, бонусное списание, бонусное начисление, способ доставки и магазин выдачи;
- должен ли сайт получать обратные изменения статуса из 1С.

## 3. Импорт каталога из файлов

Наблюдаемые файлы:

- `products.json` — основной товарный feed: описания, категории, бренд, варианты, остатки и цены;
- `pricevn.json` — цены и скидочная цена;
- `JobVN.json` — обновление контента и SEO.

Ключевые идентификаторы:

- `ID_nom` — конкретная номенклатура/вариант;
- `VariativeNomenclature` — группа вариантов;
- `Barcode` — штрихкод;
- `SKU` — локальный SKU, формируемый при импорте из входной номенклатуры;
- `GUID` — локальный GUID товара, в Legacy при создании берётся из `ID_nom`.

Реальные обезличенные примеры сохранены в [legacy-feed-samples.json](legacy-feed-samples.json).

## 4. Бонусные операции

По коду подтверждены только:

- чтение баланса через `GetBonusAccum/{Code}`;
- локальный расчёт допустимого списания и начисления;
- запись `bonus_plus` и `bonus_minus` в заказ.

Отдельного API-метода 1С для списания/начисления бонусов, transaction ID, reversal или ledger в Legacy не найдено. Поэтому нужно отдельно запросить у 1С:

- метод резервирования бонусов;
- метод подтверждения списания после оплаты;
- метод отмены/возврата бонусов;
- метод начисления после выполнения заказа;
- идемпотency key и внешний идентификатор операции;
- поведение при отмене заказа и частичном возврате.

## 5. Ошибки, безопасность и эксплуатация

В наблюдаемом коде нет единого формата ошибок WORKAPP/1С, явного claim/lease механизма для заказов или описанного retry policy. Также нужно подтвердить:

- HTTP-коды и JSON-формат ошибок;
- авторизацию и ротацию ключей;
- таймауты, rate limits и лимиты размера запроса;
- аудит запросов без записи персональных данных в логи;
- HTTPS и проверку сертификата;
- версионирование API;
- тестовый контур и тестовые идентификаторы;
- правила обратной совместимости на период миграции.

## 6. Статус готовности контракта

| Область | Известно из кода | Требуется подтверждение |
|---|---|---|
| Клиент по телефону | endpoint и поля `Discount`, `Code`, `Name` | auth, ошибки, обязательность полей, формат идентификаторов |
| Бонусный остаток | `GetBonusAccum/{Code}`, поле `Bonus` | ledger, списание, возвраты, идемпотентность |
| Обновление клиента | POST с `Phone`, `Name`, `Surname`, `BirthDate` | ответ, валидация, ошибки, source of truth |
| Заказы в 1С | pull по `1c = 0`, ack по `order_id` | статусы, повторы, обратный обмен, payment/bonus semantics |
| Каталог | три JSON-фида и ключи номенклатуры | SLA, версия фида, watermark, удаление/архивирование |
